## 按优先级排序的问题

### 1. P1：未授权日历时，服药提醒开关无法正常切换

**触发条件：** 保持日历同步关闭，且未授予日历权限；尝试关闭默认开启的服药提醒，或切换该开关。

**影响：** 开关会报错并恢复旧值。添加或修改药品也会产生“提醒同步失败”的提示，即便系统闹钟已经排好。用户被一个未启用的可选功能阻挡。

**代码路径：** `setMedicationReminderEnabled` 保存开关后调用 `resyncAll`；后者无条件调用日历 `rebuild`。`rebuild` 在判断同步开关之前检查日历权限并返回 null；协调器将 null 当作错误，设置仓储随后回滚服药提醒开关。

位置：[MedicationReminders.kt:124](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/reminder/MedicationReminders.kt:124>)、[MedicationCalendarSync.kt:47](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/data/calendar/MedicationCalendarSync.kt:47>)、[DefaultSettingsRepository.kt:85](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/data/repository/DefaultSettingsRepository.kt:85>)。

**建议：** 将闹钟同步与日历同步结果分开。日历从未启用且没有待清理日程时跳过日历操作；以前创建过日程、现在权限被撤销时，将清理状态记为待重试，仍允许用户关闭应用内提醒。测试“从未授权”“撤销权限”“关闭同步后残留日程”三种状态。

**证据级别：** 完整调用链静态确认，未在 Android 设备上执行。

### 2. P1：修改服药时间会删除该时间点全部历史打卡

**触发条件：** 药品 08:00 的时间点已有历史打卡，将时间改为 08:30 并保存。

**影响：** 所有关联旧时间点的打卡记录被删除，以后导出的备份也无法包含这些历史。单纯修改未来计划会改变过去已经发生的记录。

**原因：** `updateMedicationWithTimes` 根据时间字符串匹配，移除不在新集合中的旧时间点，再插入新时间点；`medication_intake_logs.timeId` 使用 `ON DELETE CASCADE`。现有差量更新只保护未改变时间的历史。

位置：[MedicationDao.kt:115](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/data/db/dao/MedicationDao.kt:115>)、[MedicationEntities.kt:44](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/data/db/entity/MedicationEntities.kt:44>)。

**验证：** 使用 `app/schemas/com.example.bloodpressurerecord.data.db.AppDatabase/7.json` 中实际建表 SQL，开启外键，在内存 SQLite 中插入药品、08:00 时间点和 1 条日志，再按 DAO 路径删除旧时间点、增加 08:30 时间点。日志数由 1 变为 0。此验证覆盖数据库行为，不替代 Android UI 测试。

**建议：** 将历史打卡与可修改的提醒计划分开建模。历史保存当时的药名、剂量、计划时间快照；旧计划停用或归档，新计划设置生效日期。明确“修改时间”和“清除历史”是不同操作，并补迁移及回归测试。

### 3. P2：导入范围选择无法控制用药数据写入

**触发条件：** 选择含用药数据的 v4 备份，在预览中取消全部勾选，或仅选择恢复用户资料，然后确认导入。

**影响：** 药品、每日时间点和打卡仍被写入，已匹配药品的启用状态还可能被覆盖。界面提示文件“包含”用药数据，但没有选项说明这些内容必定恢复。

**原因：** 四个 `BackupImportOptions` 字段均不控制用药恢复；事务末尾无条件调用 `importMedications(preview)`；确认按钮也未在无选项时禁用。

位置：[BackupImportService.kt:230](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/data/repository/backup/BackupImportService.kt:230>)、[SettingsDataManagementScreen.kt:289](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/ui/settings/SettingsDataManagementScreen.kt:289>)。

**建议：** 增加“恢复药品与打卡”选项并显式传到导入层；空选择不允许提交。预览区区分新增、合并与覆盖，尤其要显示药品启用状态变化。补测全不选、只恢复资料、只导入测量、只恢复用药四种情况。

**证据级别：** UI、选项模型与数据库写入路径静态确认。

### 4. P2：单组旧记录恢复编辑草稿后无法保存

**触发条件：** 编辑通过旧版或备份导入的单组读数记录，保存编辑草稿后重新进入，或恢复对应 SavedStateHandle。

**影响：** 同一条记录最初可以编辑保存，恢复草稿后却要求填写第二组，阻止用户仅修改备注或时间。

**原因：** 代码在 `restoredDraft != null` 分支提前返回，跳过根据原记录计算 `minimumReadingCount`，导致仍使用默认的 2 组限制。

位置：[EditSessionViewModel.kt:121](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/ui/history/EditSessionViewModel.kt:121>)。

**验证：** 临时 JVM 测试使用同一个单组 `SessionRecord`，分别创建普通编辑 ViewModel 和已恢复草稿的 ViewModel：前者 `canSave=true`，后者 `canSave=false`，提示 `第2组：请填写收缩压和舒张压。`。该诊断测试断言了现有异常行为，执行通过；不是声称缺陷已修复。

**建议：** 先从原记录恢复平均策略和最少读数组数，再应用草稿。增加单组历史记录通过 SavedStateHandle 和文件草稿恢复的回归测试。

### 5. P2：超过 5,000 条记录后，备份导出没有可用路径

**触发条件：** 本地记录超过 5,000 条后尝试导出明文或加密备份。

**影响：** 导出被拒绝，提示“请先按时间范围拆分”，但当前导出页面和仓储 API 没有日期范围或拆分参数。长期用户无法通过应用完成备份或换机迁移。

**原因：** 导出始终读取全部记录，再按导入上限拒绝；文件超过 10 MB 时也提示分批导出，但没有分批实现。

位置：[BackupExportService.kt:36](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/data/repository/backup/BackupExportService.kt:36>)、[DefaultSettingsRepository.kt:237](<E:/blood pressure record/app/src/main/java/com/example/bloodpressurerecord/data/repository/DefaultSettingsRepository.kt:237>)。

**建议：** 保留合理的导入保护上限，实现按日期分段或自动拆包。先检查范围和规模，再读取及序列化数据。验收 5,000/5,001 条记录、跨多个包恢复、空测量但含用药，以及超过文件大小限制的情况。

**证据级别：** 导出链路与界面/API 静态确认，未构造 5,001 条实机数据。

## 开发顺序与工程建议

### 第一阶段：完成可靠性修复

优先修复问题 1、2，再处理导入选择和单组草稿。验收标准应是“用户关闭提醒后确实保持关闭”“修改计划不删除过去的打卡”“未选择的数据零写入”“合法旧记录恢复草稿后仍可保存”。把这些行为写成自动化回归测试，避免只断言实现细节。

### 第二阶段：让已有集成测试真正进入发布门槛

[build-release.yml:33](<E:/blood pressure record/.github/workflows/build-release.yml:33>) 目前运行 `assembleDebugAndroidTest`，只构建测试 APK，没有执行仪器测试。因此 Room 迁移、数据库事务和备份往返测试不会阻止当前 CI 发布。

建议为 PR 配置至少一个 Android 模拟器任务执行现有仪器测试；发布时增加旧版本数据库升级到当前版本的完整路径、Android 26 与当前目标 API 的兼容验证。Android 官方也建议数据库实现测试运行在 Android 设备上，可使用构建管理设备组织执行：[数据库测试](https://developer.android.com/training/data-storage/room/testing-db)、[构建管理设备](https://developer.android.com/studio/test/managed-devices)。

### 第三阶段：完善备份产品流程

先完成可用的分批导出与恢复，再考虑新功能。增加“上次成功备份”和按时间跨度判断的本地提醒，提供能在空数据库完整恢复的验收流程。测量、设置、药品、提醒重排、小部件刷新应返回分项结果；数据库已经写入但外部同步失败时，应能单独重试。

### 第四阶段：围绕中老年使用场景验收界面

当前未提交改动已加入药品删除确认，并在处理深色语义色、日历图例换行和录入保存入口；不要直接把 9 月 9 日报告中的旧问题当成仍未修复。

下一步用有数据的场景验收：窄屏、系统字体 1.5/2.0、浅色/深色、键盘展开、正常及异常结果、长药名和多时间点；确认读数完整可见、核心按钮可达、状态不只靠颜色区分。当前无设备，本次不对界面实际可读性作通过结论。

### 持续维护

- 保留现有分层，优先把 `SettingsViewModel` 中资料、备份和提醒流程拆成独立状态与操作，避免一个页面的异步反馈覆盖另一个操作。
- 对闹钟、日历、时钟引入可替换接口，补失败状态、权限撤销、并发更新的测试，减少对真实系统服务的依赖。
- 将用药历史模型调整与备份格式演进放在同一计划内，继续兼容已有 v2/v3/v4 文件。
- 清理 README 的重复章节和环境矛盾：前部仍写 SDK 35 / Gradle 8.7，后部为 API 36 / Gradle 8.11.1。使用构建配置作为版本事实来源。
- 对 Lint 的依赖与库内告警逐项判断实际调用路径，不将“存在可升级依赖”等同于已确认的业务漏洞，也不要一次性升级全部库后再排查兼容问题。

## 保留的基础

领域计算与 UI 分离；原始读数及平均策略持久化；Room 显式迁移；备份预览后提交且测量写入采用事务；文件大小与解压限制；加密容器头部参与认证；Release 不回退 Debug 签名。这些实现值得保留。主要薄弱点集中在跨模块副作用、用药历史生命周期和未被 CI 实际执行的集成测试。
